# 关键设计决策

本章记录“为什么这样设计”，以及每个决定的**代价**。做技术选型时先读这里，
可以避免把框架的边界当成缺陷反复追问。

---

## ADR-01 用插件注册表替代 if 链

**背景**：v1 在 `Init`/`SafeExit`/`checkAll` 中用十几段
`if strings.Contains(used, "xxx")` 硬编码组件。

**决策**：定义 `plugin.Plugin` + 包级注册表，内置插件在 `RegisterBuiltins` 中注册。

**收益**：新增组件不改框架入口；初始化/关闭/健康检查有统一顺序。

**代价**：注册表是全局单例，测试需要隔离；`Enabled()` 的判定仍由各插件自行实现
（因此保留了子串匹配的历史问题）。

---

## ADR-02 探针与指标最先注册

**背景**：Gin 在路由注册时把当前中间件链快照进节点，后 `Use` 不回溯。

**决策**：`baseRouter` 先挂 `/health/*`、`/metrics`，再 `Use` 全局中间件。

**收益**：探针不会被 JWT/Casbin/限流拦截，K8s 与 Prometheus 永远可达。

**代价**：这两个端点不走业务中间件；若需要限流，必须自行在 handler 内处理。
另外，`EnableHealth()` 在业务 `Use` 之后调用时，后挂的探针会带上先前中间件——
这是使用顺序约束，不是框架缺陷。

## ADR-03 错误码与 HTTP 状态分离

**背景**：v1 所有错误返回 HTTP 200，网关无法按状态码重试/路由。

**决策**：`errcode.Definition{Code, HTTPStatus, MessageKey, Module}`，
`NoRoute` 返 404、`Recovery` 返 500，业务用 `i18n.ErrorDef` 输出。

**收益**：语义正确，可被网关、SDK、监控直接消费。

**代价**：业务 handler 必须显式使用 `def.HTTPStatus`；忘记改仍会返回 200。
`Code` 与 `HTTPStatus` 是两套编号，排查时要先区分。

## ADR-04 负载均衡放在客户端库内

**背景**：v1 `GetServiceURL` 只返回单实例，无法做多实例分流。

**决策**：注册中心新增 `GetServices`；`pkg/loadbalancer` 提供 4 种策略；
`client` 先选点，失败再回落 v1 单实例逻辑。

**收益**：零破坏升级；不引入 Sidecar。

**代价**：策略名与配置键分散（脚手架用 `round`，代码只认 `round_robin`）；
短名未命中静默回落，线上策略可能与预期不符。

---

## ADR-05 OpenTelemetry 只做抽象

**决策**：`pkg/otel` 仅依赖 `go.opentelemetry.io/otel` 与 `otel/trace`，
不引入 SDK/Exporter；业务调用 `SetTracerProvider` 才真正生效。

**收益**：不强迫所有使用方承担 SDK 依赖与初始化成本。

**代价**：无自动插桩；只有 `client` 调用与手动 `StartSpan` 产生 span。

---

## ADR-06 超时用 goroutine 兜底

**背景**：当前 `grequests` 版本不支持可取消的 `context`。

**决策**：`CallResilientCtx` 用 `goroutine + timer` 实现“到点返回”。

**收益**：调用方不再被慢下游无限阻塞。

**代价**：底层 HTTP 请求不会被取消，连接/协程可能残留到自然结束。
高并发 + 慢下游场景需要评估连接池与资源占用。

---

## ADR-07 兼容壳只保留一个 release

**背景**：v2 把对外包从仓库顶层收拢到 `pkg/`。

**决策**：`logs/` 保留 re-export 别名壳（`.../v2/logs`），其余走迁移文档 + sed。

**收益**：v2 早期代码升级成本低。

**代价**：双路径并存；从 v1（无 `/v2`）升级仍需改 module 路径，别名壳替代不了。

## 与外部方案的边界

| 能力 | MGin 做法 | 何时应交给外部 |
|------|-----------|----------------|
| 重试 | 客户端库内指数退避 | 已在网关/Mesh 配重试时，关闭客户端重试避免放大 |
| 熔断 | 进程内 per-instance | 需要全局熔断/配额时用 Mesh 或服务治理平台 |
| 限流 | 单实例内存计数 | 多副本需精确限流时用 Redis 令牌桶/网关 |
| 路由/灰度 | 无内置条件路由 | 用网关/服务网格；框架只负责被发现 |
| 鉴权 | JWT + Casbin 平铺 ACL | 需要 OAuth2/OIDC/细粒度 ABAC 时接外部 IdP |
| 配置 | YAML + 配置中心拉取 | 需要灰度推送/审计时用专业配置平台 |
| 任务 | 单机 cron | 需要分片/故障转移时用 XXL-Job/分布式调度 |

## 设计原则清单

1. **默认可用**：所有能力有合理零值/默认值，配置缺失不 panic。
2. **显式装配**：不扫描、不注入；`main` 里能看到所有副作用。
3. **失败隔离**：单插件失败不阻断启动；单 handler panic 不拖垮进程。
4. **可观测优先**：探针/指标先于业务中间件注册。
5. **向后兼容**：签名不变，行为变化必须进 CHANGELOG。
6. **依赖克制**：能标准库实现就不引第三方（熔断器即例）。

这些原则也解释了现有的一些“不完美”（如 `Check()` 恒 nil、配置键未接线）——
它们属于待修债务，不是设计意图。清单见
[09 · 已知问题](../11-appendix/03-migration-and-issues.md)。
