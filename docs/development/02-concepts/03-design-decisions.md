# 关键设计决策

记录「为什么是这样」，帮助有经验的开发者快速建立心智模型，也作为修改框架前的约束。每条决策都可在代码中验证。

---

## D1. 库（library）而非 Sidecar / 框架容器

**决策**：MGin 是 `import` 进业务进程的库，`NewApp` 返回 `*App`。

**原因**：部署形态简单（单二进制 + 配置），无额外网络跳数与运维组件；符合团队「一个服务一个进程」的现状。

**代价**：无法跨语言；全局单例使一个进程只能有一个 App；升级框架需要重新编译业务。

**对比**：与 go-micro/Kratos 的「框架 + 插件」类似，但没有代码生成/IDL，也没有独立控制面。

---

## D2. 配置用 `used` + `prefix` 两级声明

```yaml
go:
  config:
    used: "mysql,redis,nacos"
    prefix: { mysql: mysql, redis: redis, nacos: nacos }
```

**原因**：组件自注册、按需初始化；业务不引入未使用的依赖时零开销；子配置可按环境拆分。

**代价**：`used` 是**子串匹配**，组件名互相包含会误启用；组件多时配置重复。

**约束**：新增组件必须同时登记 `initResources/closeResources/checkAll/SafeExit` 与 `prefix` 字段，否则「启用了但不生效」。

---

## D3. 探针与指标最先注册

**决策**：`baseRouter()` 中先注册 `/health/*`、`/healthz`、`/metrics`，再 `Use` 任何中间件。

**原因**：Gin 在注册路由时快照当前中间件链；后挂的 jwt/casbin/ratelimit 不会作用到已注册路由。这样 K8s 探活与 Prometheus 抓取不会被 401/限流拦截。

**代价**：`App.EnableHealth()` 在 `NewApp` 之后调用时，探针仍会带上默认链（trace/postlog/cors/recovery），但不会带业务后加的中间件；需要完全干净时用配置开关。

**验证**：`app.go` 的 `mountHealth` 注释与 `baseRouter` 顺序。

---

## D4. 业务错误统一 HTTP 200 + `status`

**决策**：`models.Result{status,msg,data,page}`；404 与 panic 也返回 200 + `status=1000/1001`。

**原因**：前端与调用方只需解析一种信封；避免网关把业务错误当传输错误重试。

**代价**：HTTP 状态码不能反映业务成败，监控/网关需要解析 body；与 REST 纯正主义冲突。

**例外**：JWT 401、Casbin 403、iplimit 403、ratelimit 可配 `httpStatus`（默认 200 + 1011）。

---

## D5. 全局单例

**决策**：`config.Config`、`db.Mysql/Mongo/Redis/Sqlite`、`registry.Registry`、`casbin.Casbin`、`job` 管理器都是包级单例。

**原因**：库形态下减少参数透传；与历史代码兼容。

**代价**：测试必须串行/重置；无法在同一进程跑两个隔离的 App；热重载必须串行（`reloadMu`）。

---

## D6. 定时任务内嵌进程、单机调度

**决策**：`job` 用数据库存任务与日志，进程内 cron 调度。

**原因**：不引入额外调度服务；对中小规模后台任务足够。

**代价**：多实例会重复执行；无分片、无故障转移。需要分布式调度时应外置（如 xxl-job），本模块只作为单机实现。

---

## D7. 服务发现加本地缓存装饰器

**决策**：`NewCachedRegistry` 包装所有注册中心实现：TTL 缓存 + singleflight + 后台热刷新 + 无实例时降级复用旧缓存。

**原因**：绝大多数调用命中缓存，避免每次调用打注册中心；注册中心抖动时仍可调用。

**代价**：实例下线有 TTL 延迟（默认 60s）；缓存与真实状态可能短暂不一致。

---

## D8. 日志异步单消费者

**决策**：`logsink` 每个 handler 一条队列、**固定 1 个消费协程**；队列满淘汰最旧。

**原因**：保证 FIFO 与顺序可预测；避免多协程写同一目标的锁竞争。

**代价**：吞吐受单协程限制；过载时丢日志（有计数与限流告警）。

---

## D9. 泛型 DAO 而非 Repository 接口

**决策**：`MySQLDao[E schema.Tabler]` 直接暴露 GORM 能力（`DB()`、`JOIN()`），并提供 `Where*` 缓存。

**原因**：减少样板；业务可随时下沉到 GORM。

**代价**：`Dao[E]` 接口（仅 `Insert`）与实现不完全匹配；`WithContext` 修改接收者、`Updates` 不带 Where 等陷阱需要文档约束。

---

## D10. 国际化改为内置数据库字典

**决策**（jh 分支）：删除外部 `x-lang` 微服务，字典存 MySQL/SQLite（表 `{app}_i18n`），`i18n.String` 通过 `X-Lang` 解析。

**原因**：减少一个外部依赖；文案可运维直接改库。

**代价**：需要数据库；`i18n.Init()` 失败会 panic；多实例需共享同一字典库。

---

## D11. 明确的能力边界

**决策**：PostgreSQL、ClickHouse、ElasticSearch、Kafka、S3、系统管理 HTTP 模块不在本分支实现。

**原因**：jh 线只维护实际使用的技术栈；历史 README 中的相关章节是上游/规划内容。

**代价**：文档必须显式标注「未实现」，脚手架 `--db postgres|clickhouse` 会生成不可编译代码（已知缺陷）。

---

## D12. 配置重载只重载资源

**决策**：`PUT /cfg/reload` 重新加载配置并重建数据源/注册中心/job/插件，但**不重建路由、中间件、监听端口**。

**原因**：运行期重建 Gin 引擎不安全（并发写、连接中断）；资源级重载已覆盖大部分运维场景。

**代价**：修改端口、JWT 密钥、中间件开关需要重启；重载失败时保留旧连接（部分资源可能处于半新半旧状态，需要日志确认）。

---

## 修改框架前的检查

1. 是否破坏上述任一决策？如果是，先更新本文与 [需求文档](04-requirements.md)。
2. 是否引入新的全局状态？优先用参数或实例字段。
3. 是否改变默认行为？开关必须默认保持旧行为。
4. 是否新增对外可见的路径/指标/日志字段？按兼容性策略处理（见 [发布规范](../10-contributing/04-release-process.md)）。
