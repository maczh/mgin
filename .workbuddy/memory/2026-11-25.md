## pkg/db/ 与 pkg/plugin/builtins.go panic 风险审计（v2 分支）

- 工作流：software-company 专家团（架构师静态评审 → 工程师最小复现 → QA 独立复核），三份报告落盘在 `deliverables/software-company/panic-audit-2026-11-25/`（01-architect-review.md / 02-engineer-repro.md / 03-qa-verification.md）。**未改任何生产代码**，只新增 deliverables。
- 核心结论：仅 Redis/Mongo 的「无锁 + 可写共享 map」是 P0，会触发 Go runtime `fatal error: concurrent map read and map write`（`throw`，recover 无效）；已用 `-race` 与默认模式双重动态复现。根因是近期 9825b9b 等提交只加固了 MySQL，Redis/Mongo/SQLite 未同步加固。
- 关键代码事实：
  - `app.go:387` 的 `SafeExit()` 在 `app.go:393` 的 `servers.Shutdown()` **之前**调用，`mgin.go:207-211` 只排空日志/i18n 就 `plugin.CloseAll` 关闭 DB → 在途 HTTP 请求与 DB Close 并发窗口真实存在。
  - `sqlite.Close` 的 panic 实际在 `m.sqlite.DB()` 内部（gorm v1.31.0 `gorm.go:413`），不是 `db.Close()`；gorm.Open 失败后 `db.DB()` 仍返回有效 `*sql.DB`，生产 Init 失败路径不触发该 panic，优先级已下调。
  - `plugin.InitAll`/`HealthAll` 无 recover；`CloseAll` 有 recover 但吞掉 panic 不记日志；`Register` 未拦 typed-nil；`builtins.enabled()` 用 `strings.Contains` 会子串误启用。
- 修复方向：以 `mysql.MysqlClient` 为模板，给 RedisClient/Mongodb 加 `sync.RWMutex` + `closed` + RCU（锁外建连、锁内发布、锁外关旧），`GetConnection` 锁内取本地变量并做 `conn==nil` 守护；插件层补齐 recover 与日志。
- 环境注记：Bash 的 PATH 无 go，需 `export PATH=/usr/local/go/bin:$PATH`；proxy.golang.org 常 Bad Gateway，用 `GOPROXY=https://goproxy.cn,direct go mod download go.mongodb.org/mongo-driver` 解决。
